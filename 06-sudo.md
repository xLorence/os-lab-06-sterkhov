# Отчет по заданию 6 (Ограниченное правило sudo)

**Содержимое файла правил `/etc/sudoers.d/student2-lab`:**
`student2 ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart cron`

**Вывод `sudo -l` для student2:**
```
User student2 may run the following commands on debian-vm:
    (ALL) NOPASSWD: /usr/bin/systemctl restart cron
```

Результаты проверки:
* Разрешенная команда: sudo systemctl restart cron выполнилась успешно без запроса пароля, код возврата 0 подтверждает отсутствие ошибок.   
* Запрещенные команды: При попытке выполнить sudo systemctl restart ssh и sudo cat /etc/shadow система выдала жесткий отказ (Sorry, user student2 is not allowed to execute...). Правило работает строго в заданных границах.
   
### Почему visudo безопаснее прямого редактирования /etc/sudoers:
Утилита `visud`o перед сохранением проверяет файл на синтаксические ошибки. Если открыть основной файл `/etc/sudoers` обычным редактором (например, nano или vim) и допустить там опечатку, права sudo сломаются во всей системе. Никто, включая администратора, больше не сможет выполнить команды от имени `root`, и систему придется восстанавливать через спасательный режим (LiveCD). `visudo` просто не даст сохранить сломанный файл.

### Почему давать sudo на vim, less или find опасно:
Многие безобидные на первый взгляд утилиты умеют запускать внутри себя командную оболочку (`shell`). Если дать обычному пользователю право запускать `sudo vim` (чтобы он мог править конфиги), он может нажать в редакторе `:sh`, и у него откроется полноценная командная строка. Но поскольку сам `vim` был запущен с правами `root`, то и открытый из него `shell` тоже получит права `root`. Это классическая уязвимость (описанная в проекте GTFOBins), которая равносильна выдаче пользователю полных прав на весь сервер.
